# Betna MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Betna’s Kenya/Uganda trust-first property marketplace: public discovery, individual-owner listing submission, employee field verification, protected inquiry handling, and manual commission tracking.

**Architecture:** A pnpm/Turborepo TypeScript modular monolith has `apps/web` for localized, server-rendered Next.js public/portal experiences and `apps/api` for NestJS domain workflows. PostgreSQL/PostGIS is authoritative; Redis/BullMQ handles retryable work and S3-compatible storage separates public media from private inspection evidence.

**Tech Stack:** Next.js App Router, NestJS, TypeScript, PostgreSQL + PostGIS, Prisma, pnpm/Turborepo, Tailwind CSS, next-intl, Zod, Vitest, Playwright, Redis/BullMQ, S3-compatible storage, Docker Compose.

**Spec:** `docs/superpowers/specs/2026-11-06-betna-mvp-design.md`

## Global Constraints

- Implement a modular monolith, not microservices; the NestJS API is the future mobile-client boundary.
- Launch only Kenya/KES and Uganda/UGX; keep country/city/territory data extensible.
- Public UI, emails, metadata, and portals support English and Tigrinya; both are LTR.
- Public listings require verification and admin publication; exact address, evidence, and owner identity are never public.
- Visitors may inquire without an account; owners are individual accounts only and can manage several listings.
- Listing pages show mandatory local prices and separate short-stay/long-term views.
- No payment gateway, instant booking, travel integration, agency account, or dynamic FX in this MVP.
- Verification expires after one year; private inspection evidence is retained indefinitely.
- Use Luna at high reasoning effort for implementation work.

## Review Focus

- Overlapping short-stay inquiries: only the first confirmed inquiry atomically blocks dates and declines all overlaps (Task 11 test).
- Pending or expired/fraudulent listings: they never appear in public results, sitemaps, or direct public routes (Task 9 test).
- Private coordinates, evidence, and owner data: a visitor API response must not disclose any of them (Task 10 test).
- Offline verifier submission: a report cannot become approvable before all required evidence has synced and validated (Task 11 test).
- Commission evidence: a commission cannot be marked due without a reported conversion and staff-verified first-payment evidence (Task 11 test).

## Self-review

- **Spec coverage:** Tasks 1–4 deliver the foundation, identity, i18n and portals; Tasks 5–9 implement property workflows, media, verification, translations, public search and SEO; Tasks 10–11 implement contacts, inquiries, availability, conversion and commissions; Task 12 delivers operations. Deferred payments, travel, FX and agencies are intentionally excluded.
- **Step scan:** Every task starts with a focused failing test, has an explicit implementation boundary, and ends with a named verification command and commit.
- **Type consistency:** Shared `contracts` provides all cross-app status types; service names defined in task interfaces are used only by later dependent tasks.
- **Review Focus:** Each of the five listed risks has an explicit owner task/test.
- **Proportion:** The plan defines interfaces and verification without embedding application implementation bodies.
